# Task: Optimize Collective Sketch Generation

Optimize compact broadcast sketch generation for a `${GPU_NUM}`-GPU cluster targeting `${Collective}`.

You are evolving Python code that implements `construct_sketches()` and returns exactly **one** candidate single-root broadcast sketch in a compact DSL.

Return only Python code. Do not include explanations, Markdown, simulator calls, or multiple sketches.

## Core Idea

Do **not** write a full `${Collective}` schedule directly.

Your sketch only describes how the chunk initially owned by **GPU 0** is broadcast to every other GPU. The evaluator will validate the DSL, convert it into SyCCL sketch JSON, rotate the single-root tree across all `${GPU_NUM}` root GPUs, expand the result into full `${Collective}` direct events, and simulate the final GPU-to-GPU event schedule.

A good sketch should be fast for the target collective  `${Collective}` after the same pattern is rotated across all roots.

## Optimization Objective

Maximize:

```python
combined_score = coll.byte / simulated_time_us
```

Since `coll.byte` is fixed, the practical objective is to minimize simulated `time_us`.

## Topology

- **Layer**: a distinct tier in the topology.
- **Group**: a group under the same layer.
- Nodes in the same layer/group can communicate through that layer.
- Nodes in different groups must use other layers for connectivity.

Topology and link specs:

```text
${TOPOLOGY}
```

Interpretation:

- Layer 1, such as intra-host GPULINK, is fast and usually good for host-local fanout.
- Layer 3 or 4, such as inter-host switch links, has lower bandwidth and nontrivial latency.
- Avoid rotated `${Collective}` patterns that overload leaf links with serialized sends.
- DO NOT use layer `2` in the DSL for this task. layer `2` is GPU-NIC link and will be rejected in DSL sketches.

## Return Format

Implement:

```python
def construct_sketches():
    ...
```

Return one sketch as a list of compact transmissions.

Preferred tuple form:

```python
(step, chunk, layer, group, srcs, dsts)
```

Dict form is also accepted:

```python
{
    "step": 0,
    "chunk": 0,
    "layer": 1,
    "group": 0,
    "srcs": [0],
    "dsts": [1, 2, 3],
}
```

`srcs` and `dsts` may be either a single GPU id or a list of GPU ids.

If `srcs` contains multiple GPUs, all listed sources must already have the chunk before this step. During direct-event expansion, destinations are assigned across the listed sources in order, expressing parallel fanout from several relays inside one layer/group.

## Validity Constraints

- Use only layers `1` and `3`.
- All `srcs` and `dsts` in a transmission must be inside the specified `layer/group`.
- GPU ids must be integers in `0 .. ${GPU_NUM} - 1`.
- GPU 0 starts with the root chunk and must not appear as a destination.
- Every GPU from `1` to `${GPU_NUM} - 1` must be reached exactly once.
- A GPU may be used as a source only after it received the chunk in an earlier step, except GPU 0.
- Same-step forwarding through a newly reached GPU is invalid.
- Dependent steps must be strictly increasing but independent steps do not need.
- No transmission may contain duplicate destination ids.
- No sketch may deliver to the same destination GPU more than once.

## Design Guidance

Think in two stages:

1. Design an efficient broadcast tree for chunk 0.
2. Reason about what happens when the same tree is rotated across all `${GPU_NUM}` chunks for `${Collective}`.

Explore relay choices, fanout timing, dependency depth, multi-source fanout, and the balance between fast intra-host fanout and lower-contention inter-host communication.

## Evaluator Metrics

- `combined_score`: the primary score to maximize; equals `coll.byte / simulated_time_us`.
- `validity`: `1.0` for a valid sketch that simulates successfully, `0.0` otherwise.
- `bottleneck_profile`: diagnostic feedback describing bottleneck transmissions on the collective critical path.

## Bottleneck Profile

`bottleneck_profile` is an array where each element corresponds to one original sketch transmission, sorted by `transmission_index`.

| Field | Meaning |
|---|---|
| `transmission_index` | Index of the transmission in the original sketch, used for stable sorting and locating the sketch entry. |
| `sketch` | Human-readable transmission description, including `step`, `layer`, `group`, source GPU list, and destination GPU list. |
| `profile_data` | Time breakdown and overall impact of this transmission on the bottleneck path. |
| `propagation_delay_portion` | Percentage of this transmission's total time spent on propagation and fixed scheduling delay. |
| `transmission_time_portion` | Detailed transmission-phase breakdown. Its subfields use the same total-time denominator as `propagation_delay_portion`. |
| `serialize_time` | Percentage of this transmission's total time during which the link is actually transmitting data. |
| `queue_wait` | Percentage of this transmission's total time spent waiting due to link or queue contention. |
| `total_time_share` | Percentage of the full collective completion time accounted for by this transmission's total time. |

For a nonzero-duration transmission:

```text
propagation_delay_portion + serialize_time + queue_wait = 100%
```

`serialize_time` and `queue_wait` are relative to the total time of this transmission, not only to `transmission_time_portion`.
