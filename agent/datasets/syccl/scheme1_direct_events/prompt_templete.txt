Optimize Collective sketch generation for a ${GPU_NUM} GPU cluster ${Collective} target.

You are evolving Python code that returns candidate single-root broadcast sketches
in a compact DSL. The target collective is ${Collective}, but you do not write a full
${Collective} schedule directly. Instead, your sketch describes how the chunk initially
owned by GPU 0 should be broadcast to every other GPU. The evaluator expands that
single-root broadcast tree into one analogous tree per source chunk/root GPU using
topology-preserving rotations, then simulates the resulting full GPU-to-GPU
${Collective} event schedule. This means a good compact tree must be fast for root 0
and, more importantly, should create low contention after the same pattern is
rotated across all ${GPU_NUM} roots.

The evaluator validates your DSL, converts valid sketches into SyCCL sketch JSON,
expands them into ${Collective} direct events, and runs a simulator. You only need to
return candidate sketches; do not call the simulator yourself.

Optimization objective:

    combined_score = coll.byte / simulated_time_us

Higher `combined_score` is better. Because `coll.byte` is fixed for this task,
the real objective is to minimize the flow-sim-rs `time_us` value for the best
returned candidate sketch.

The following is the topology description: We define Layer as distinct tiers within the topology, and GROUP as separate groups under the same tier. Nodes in the same group can communicate solely via links belonging to that tier, while nodes from different groups must rely on links from other tiers to establish connectivity.

Interpretation:
- IntraHost GPULINK like layer 1 is relatively fast and should usually be used for host-local fanout.
- InterHost link via switch like Layer 3 has much lower bandwidth and nontrivial latency, so avoid creating a
  rotated ${Collective} pattern that overloads leaf links with many serialized sends.
- Layer 2 just describes how GPU is connected with SWITCH. BUT you can not use the layer 2 topo in dsl for this task, because the evaluator will reject any sketch that uses layer 2.

Required return format:
- Implement `construct_sketches()`.
- Return ONLY ONE sketch .
- A sketch is a list of compact transmissions.
- Preferred compact transmission form:

```python
(step, chunk，layer, group, srcs, dsts)
```

- `srcs` and `dsts` may each be a single GPU id or a list of GPU ids.
- If `srcs` contains multiple GPUs, all listed sources must already have the chunk before this step. During direct-event expansion, destinations in that transmission are assigned across the listed sources in order, which can express parallel fanout from several relays inside one layer/group.
- Dict form is also accepted:

```python
{"step": 0, "layer": 1, "group": 0, "srcs": [0], "dsts": [1, 2, 3]}
```

Validity constraints:
- Use only layers 1，3.
- A transmission's srcs and dsts must all be inside the specified layer/group.
- GPU ids must be integers in 0..${GPU_NUM}-1.
- GPU 0 starts with the root chunk.
- Every GPU 1..${GPU_NUM}-1 must be reached exactly once; GPU 0 must not appear as a dst.
- A GPU may be used as a source only after it has received the chunk in an earlier step, except GPU 0.
- Dependent steps must be strictly increasing. Same-step forwarding through a newly reached GPU is invalid.
- No transmission may have duplicate dst ids, and no sketch may deliver to the same dst twice.


Design guidance:
- Think in two stages: first design an efficient broadcast tree for chunk 0, then reason about what happens when the same tree is rotated to all ${GPU_NUM}chunks for ${Collective}. 
- Try different relay GPUs, fanout timing, and dependency depths.
- Consider using multiple already-reached relays as `srcs` for a later fanout 
- ONLY return ONE sketch one time.

Evaluator metrics:
- `combined_score`: the only score to maximize; equals `coll.byte / simulated_time_us`.
- `validity`: 1.0 for a valid sketch that simulates successfully, 0.0 otherwise.
- `bottleneck_profile`: flow-sim-rs critical-flow-chain feedback. The current simulator returns `critical_flow_chain` with the latest flow id and chain entries. Use it as a diagnostic clue, not as the score.
